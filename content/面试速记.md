# 业务具体信息
```bash
1.用户量
	面向的是区域级的医院联合体，并不是像互联网C端那种动则上亿用户，我们平台的注册医护/管理人员大约在3000~5000人，高峰期并发量大概在500-800QPS
	
2.日志量
	我们接入20+个核心微服务，每个服务平均每秒产生约50-80条日志，高峰期每天产生日志约600-800gb左右，按照一聊数据留存法规，需要热数据保留7天，冷数据保留至少6个月。如果只算热数据，集群存储规模就在5T-6T左右
	
3.为什么要上这么大配置
	1.应对突发洪流和数据断层（故障冗余）
	医院业务有典型特征：早上8:00-9:00是挂号缴费高峰，QPS瞬间暴涨3倍，如果配置只按平均负载来买，高峰时CPU飙到90%，必然导致服务超时，患者排队堵在窗口，这是重大生产事故。我们预留了 60% 以上的资源余量，确保单台物理机宕机时，K8s能瞬间将Pod驱逐到其他节点，且剩余节点CPU不超过70%，保证业务完全无感。
	
	2. 数据库和中间件的"内存命根子"
我们的核心业务（挂号、处方、支付）涉及大量热点数据。Redis缓存如果内存只有64G，热点数据被LRU（最近最少使用）算法挤出去，缓存命中率掉到50%以下，数据库就会扛不住。我们把Redis配到128G，就是为了**缓存命中率维持在95%以上**，直接给MySQL‘挡子弹’。同样的，MySQL配256G内存，是因为InnoDB缓冲池（Buffer Pool）越大，磁盘IO越少，这是物理定律决定的。

	3. 合规与容灾（主备切换时长）
国家卫健委对三级等保和医院信息互联互通有明确要求，核心业务 年度可用性需达到99.99%（即全年宕机不超过52分钟）。我们的双活数据中心和Keepalived VIP切换，依赖 万兆网卡 的低延迟，确保切换时间控制在 3~5秒 内。如果换成千兆网卡或低配服务器，切换时数据同步延迟高，就可能丢数据（RPO>0），这在医疗场景是绝对不允许的。”

	4.补充
	当然，高配置不代表浪费，会通过hpa结合prometheus自定义指标，在凌晨低峰期自动缩容Pod副本数，降低资源占用；同时利用 分层存储，将超过7天的冷日志从ES热节点转移到廉价的 S3/MinIO对象存储（或Loki），从而控制了存储成本。这个配置是‘为极端场景买单’，但通过自动化运维做到了‘弹性成本’。
```

```bash
3主5从

追问"为什么用flannel不用calico"：
	解释：当时确实把calico也部署调试过，但是实际调试过程中发现几个问题：
		1.Calico 需要配置 BGP 路由，我们的测试集群网络环境比较复杂，跨网段的时候 BGP 邻居老起不来，排错花了好几天
		2.那会儿 K8s 刚上手，Calico 出问题日志看不太明白，社区文档也比较深
		3.当时项目时间紧，领导要求先把容器化流程跑通，不能卡在网络这环
		
		
追问"docker 1.24后不支持了怎么解决"：
	解释： k8s 1.24之后官方移除了dockershim，我们使用的是社区维护的cri-dockerd来做适配层，让docker ce继续作为运行时，选这个方案主要是因为运维团队对docker更加熟悉，排查容器问题更加顺手，cri-dockerd本身也很稳定
```

## 统一运维平台监控告警与日志排查
![[面试速记-20260820210549.png]]
```bash
总共分为四层：数据源层、采集层、存储与处理层、展示与告警层

追问"为什么有了elk还要对接loki"
	解释：
		1.Elasticsearch十分吃资源，我们养不起两套全量ELK
		2.Loki不会像es把每条日志的每个字段都拆开建索引，它只给日志打上标签（比如"那个服务"、"那台主机"），内容还是整块存到，存日志跟存文件一样便宜
		3.ELK留着干"精细活"，比如要查看某个订单号的完整链路，或者在海量业务日志里搜特定的异常堆栈，
		4.我们运维看概括用loki（快，省），开发深挖用ELK（准，全）
		

prometheus监控了那些指标：
	解释：
		1.基础设施层：
			cpu：使用率、负载
			内存：可用内存、swap使用率
			磁盘：使用率、inode使用率
			网络：tcp连接状态、网卡流量
		2.中间件层
			mysql：连接数、慢查询数量、ops/tps、主从复制延迟
			redis：内存使用率、命中率、连接数、key过期数量
			nginx：qps（请求量）、4xx/5xx错误率、活跃连接数
		3.容器/k8s层
			pod状态
			容器cpu/内存实际使用率
			ingress/service的请求延迟和错误率
		4.业务服务层
			用blackbox exporter做黑盒监控，定时探测业务接口的http状态码和响应时间

监控指标采集上来后对告警进行分级：
	解释：
		1.告警分级
			p0紧急：磁盘满、服务宕机、mysql主从断开 --- 立刻打电话或者发送钉钉@所有人，增加短信告警
			p1重要：cpu持续80%以上、内存泄露趋势、慢查询激增 --- 发告警到群，白天必须处理
			p2提醒：磁盘使用率超70%、非核心pod重启 --- 发邮件，周会统一复盘
			
		2.数据采集频率分层
			核心数据15s一次，非核心趋势指标1m一次，业务自定义指标5m一次
```
